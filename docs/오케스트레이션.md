# 모델 오케스트레이션 설계

여러 오픈모델을 **동시에** 활용하는 기능. 단일 모델의 약점(속도·정확도·컨텍스트)을 조합으로 보완한다.

## 모드

### 1. 라우터 (router)
작업을 분류해 가장 적합한 모델로 보낸다.
- 예: 간단한 편집 → 7B, 설계/디버깅 → 32B, 리팩터링 계획 → reasoning 모델
- 분류기: 규칙 기반 + 소형 모델 라벨링

### 2. 앙상블 투표 (ensemble)
같은 작업을 N개 모델에 병렬로 던지고 결과를 모은다.
- 다수결 / self-consistency
- 판정 모델(judge)이 최고 답 선택
- 편집이 서로 다르면 사용자에게 diff 비교 제시

### 3. 작업 분할 (divide) — "여러 모델에 나눠서 시키기"
플래너 모델이 작업을 서브태스크로 쪼개고, 워커 모델들이 **병렬로** 각자 처리한 뒤 통합한다.
- 예: "3개 파일 수정" → 파일별로 다른 모델에 할당
- 통합 단계에서 충돌(같은 심볼 수정) 검사

### 4. 초안-검수 파이프라인 (pipeline)
모델 A가 초안 → 모델 B가 리뷰/수정 → (선택) 모델 C가 테스트 관점 점검.
- 서로 다른 계열 모델을 섞으면 편향 감소 (예: Qwen 초안 + Llama 검수)

### 5. 스펙 디코딩형 협업 (speculative)
소형 모델이 빠르게 초안, 대형 모델이 검증·수정만 담당해 총 지연 감소.

## 설정 예시

```yaml
orchestra:
  mode: router            # off | router | ensemble | divide | pipeline
  models:
    fast:  { backend: ollama, model: "qwen2.5-coder:7b" }
    heavy: { backend: ollama, model: "qwen2.5-coder:32b" }
    review:{ backend: ollama, model: "llama3.1:8b" }
  router:
    rules:
      - if: "task.kind == 'simple_edit'"  then: fast
      - if: "task.kind in ['design','debug']" then: heavy
    default: heavy
  ensemble:
    members: [fast, heavy]
    judge: heavy
  divide:
    planner: heavy
    workers: [fast, heavy, review]
    max_parallel: 3
```

## 실행 인프라

- 로컬에서 여러 모델 동시 구동 시 메모리 경쟁 → 백엔드별 **모델 슬롯** 관리 (Ollama `keep_alive`, 순차 로드/언로드 옵션)
- 호스팅 API 혼합 사용 지원 (일부는 로컬, 일부는 원격)
- 모든 호출은 비동기(`httpx.AsyncClient`)로 병렬화

## 구현 우선순위

로드맵상 Phase 7. Phase 1~6에서 단일 모델 경로를 먼저 완성하고, 백엔드 추상화(`serving/base.py`)를 다중 인스턴스로 확장한 뒤 도입한다.
