## A. 에이전트 코어

| 기능 | CC | Gem | Cdx |
|---|:--:|:--:|:--:|
| 에이전트 루프 (툴 호출 → 실행 → 관찰 반복) | ✅ | ✅ | ✅ |
| 스텝/토큰 예산 및 중단 조건 | ✅ | ✅ | ✅ |
| 계획(plan) 모드 - 편집 없이 계획만 제시 | ✅ | 🟡 | 🟡 |
| 확장 사고(thinking) 토글 | ✅ | 🟡 | ✅ |
| 작업 목록(todo) 추적 및 표시 | ✅ | ➖ | 🟡 |
| 서브에이전트 - 하위 작업을 별도 컨텍스트로 위임 | ✅ | ➖ | 🟡 |

- [x] **A1. 에이전트 루프** — `loop/agent.py`: 시스템프롬프트+툴 → chat → tool_calls 실행 → tool 결과 주입 반복, 이벤트 스트림(AgentEvent), `giga agent` 명령
- [x] **A2. 예산·중단 제어** — 최대 스텝(max_steps) + 반복 가드(repeat_limit) + 토큰 예산(`giga agent --budget N`, 누적 초과 시 `stop_reason=budget` 로 중단) + Ctrl-C/CancelledError 시 부분 결과를 `stop_reason=cancelled` 로 깔끔히 반환 (`loop/agent.py`)
- [x] **A3. 계획 모드** — `giga plan "작업"`: 읽기 도구만으로 조사 → 번호 매긴 실행 계획 + "확인 필요"·"위험" 정리 출력(파일 미변경). `-x` 로 계획 확인 후 `giga agent -w --mode auto-edit` 로 넘겨 실행 (`commands/plan.py`, `loop/prompt.py` PLAN_MODE_PROMPT)
- [x] **A4. 사고 모드** — `giga agent`/`giga chat` 의 `--think` / `--think-hard`: 시스템 프롬프트에 "단계적으로 추론" / "여러 접근 비교·반례 탐색" 지시를 얹고(`loop/prompt.py` think_directive) + 백엔드 네이티브 reasoning 파라미터(D9)도 low/high 로 전달
- [x] **A5. 작업 목록 추적** — `update_tasks` 도구(모든 모드에서 사용 가능): 에이전트가 3단계 이상 작업을 체크리스트로 분해하고 단계마다 pending/active/done 갱신. 목록은 `ctx.scratch["tasks"]` 에 세션 범위로 저장, CLI 이벤트 프린터·VS Code 확장이 ✔/▶/○ 로 렌더 (`loop/task_tools.py`)
- [x] **A6. 서브에이전트** — `run_subagent` 도구: 하위 작업을 독립 컨텍스트(부모 대화 미상속)의 에이전트에 위임. 조사·요약처럼 중간 산출물이 많은 작업을 떼어내 부모 컨텍스트를 아낀다. 깊이 제한 2, 부모가 쓰기 모드일 때만 `write:true` 로 편집 허용, 승인 정책·훅·샌드박스는 부모 것을 물려받음 (`loop/subagent.py`)
- [x] **A7. 명확화 질문 (ask_user)** — 사용자만 결정할 수 있는 모호한 지점에서 에이전트가 `ask_user` 도구로 선택지/자유입력을 요청. 비대화 세션은 "가정하고 진행" 안내 반환. 시스템 프롬프트에 남용 방지 지침 (이슈 #28)

## E. 멀티 모델 오케스트레이션

- [x] **E1. 라우터** — 첫 사용자 메시지를 규칙으로 분류(TaskKind) → `orchestra.yaml` 매핑으로 세션 모델 선택. `giga route` 로 결정 미리보기 (`orchestra/router.py`). 소형 모델 라벨링은 이후
- [x] **E2. 앙상블 투표** — `giga ensemble "질문" -m A -m B [-j 판정]`: N개 모델을 같은 질문에 병렬로 돌리고(도구 미사용) 판정 모델이 사실 오류·논리 허점을 걸러 하나로 종합. `-m` 은 모델 ID 또는 `orchestra.yaml` 슬롯, 생략 시 슬롯 전체 (`orchestra/ensemble.py`, `orchestra/multi.py`)
- [x] **E3. 작업 분할** — `giga divide "목표" [-w] [--planner M]`: 플래너 모델이 목표를 3~6개 하위 작업으로 나누고(`orchestra/divide.py`), 각 하위 작업을 독립된 `giga agent` 실행으로 순차 처리(자체 컨텍스트·runlog). 같은 저장소를 건드리므로 병렬 대신 순차. `--dry-run` 으로 분할만 미리보기
- [x] **E4. 초안-검수 파이프라인** — draft 에이전트 편집 후 review 모델이 diff 검토 → `giga agent --review` / `--review-fix`(지적 반영 1회), 독립 `giga review` (`orchestra/pipeline.py`)
- [x] **E5. 스펙 협업** — `giga spec "요구사항" [-d 초안모델] [-r 검증모델] [-o 파일]`: 소형 모델이 구현 계획 초안(목표/접근/변경파일/단계/미해결질문)을 쓰고, 대형 모델이 오류·엣지케이스를 지적한 뒤 최종본을 다시 씀. 도구 미사용 (`orchestra/spec.py`)
- [x] **E6. 모델 슬롯 관리** — orchestra.yaml 이름→모델 슬롯 매핑 + `OllamaBackend.unload()`(keep_alive:0 으로 VRAM 즉시 반환). `orchestra/multi.py` `release()` 가 앙상블·작업분할·스펙협업에서 각 모델 사용 후 언로드→다음 모델 순차 실행 (`serving/ollama.py`)
- [x] **E7. 비동기 실행** — 모든 백엔드 호출 async (`httpx.AsyncClient`)
